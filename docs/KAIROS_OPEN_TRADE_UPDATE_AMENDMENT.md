## Missing capability and chosen boundary

Gate397 creates new manual trades, but a saved Open trade cannot subsequently receive later fills or an explicit Closed status in the UI. Creating a second trade to record its exit would lose identity and disconnect its original entry. This supporting P10/P12 integration amendment lets Journal history update that same open manual trade. It supports P11/P13/P14/P21 consumers without claiming P21 closure.

## UI and meaning

Journal → Trade history → an Open manual trade → Update trade. An inline compact editor shows recorded fills in a collapsible read-only list and reuses JournalExecutionFields for new entries/exits and optional new fees. Prices, quantities and times are explicit. Keep open is the default; choosing Closed requires an explicit closing timestamp. Save update commits the new facts onto the original trade, refreshes history/daily results, and existing Your Trades queries use the saved result on entry/refresh. Times use the device time zone and normalize through the existing adapter to UTC. Cancel with additions asks whether to discard them; validation/storage errors retain the form and focus an error message. Controls use existing design tokens and adapt to narrow mobile widths.

This is manual journaling. It does not schedule time-triggered closure, place orders or acquire execution prices from live market data. Saved prices, fills, fees and plans are never edited or deleted by this append operation.

## Ownership and transaction safety

- JournalOpenTradeUpdate owns only ephemeral form state, explicit action and presentation. JournalRoute owns refresh, and JournalHistoryList supplies the selected saved entry. UI performs no database queries/writes directly, calculations or provider operations.
- updateOpenManualTrade owns one new application update command. It reuses the existing exported prepareManualTrade function unchanged for validation and creation of new execution/fee records; the original saveManualTrade contract/behavior is preserved.
- The candidate trade generated by the shared validator is never stored as a new identity. The command preserves the current saved trade's id, source, creation time, symbol, market, side and opening timestamp, changing only explicitly requested status/closing time and update timestamp.
- Before writing, a single existing runKairosAtomicWrite transaction checks saved trade identity/source/status and compares the full expected header/execution/fee snapshot. It then appends new child rows and updates the header together. A stale form is rejected, including two concurrent appends sharing the same millisecond. ID collisions are checked before writes, so the existing put repository method cannot overwrite a prior fact.
- Existing plans, existing linked fees and all original executions remain byte-for-byte unchanged. All writes roll back if any new row fails. No schema, repository interface, dependency, backup format, calculation, provider or Live Bubble changes.
- P11 calculation, P12 query, P13 outcomes and P14 visualization remain their existing owners. Missing currency stays unknown; fees may keep net result unavailable. A manually closed trade with incomplete fills does not acquire an invented realized result.
